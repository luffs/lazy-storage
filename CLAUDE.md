# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

lazy-storage is a self-hosted realtime state store with offline sync, built on [lazy-watch](https://github.com/luffs/lazy-watch). A store is collections of records (JSON objects of any depth) and singletons; the server decides every change path by path against each record's clock, and clients keep the server's state (the base) with their unacknowledged ops (the outbox) replayed on top in a LazyWatch proxy, turn every local batch into an op of changes, and keep the outbox across reconnects and reloads. A relay is a follower store: a copy of the server's, read once, for working while the server is away and for fan-out. Plain ES modules, no build step, one runtime dependency (lazy-watch). The README is the pitch and the quickstart; `docs/` is the user-facing reference, a page per topic: `model.md` (collections, records and singletons, lists, conflicts, the client's base and pending, time, undo, scope), `offline.md`, `stores.md` (many stores over one socket, one socket per browser), `server.md` (persistence, migrations, backups, server-owned state, embedding, Node), `auth.md` (authentication, rules, presence, eviction), `relays.md` (the follower store, working while the server is away, spreading the load), `limits.md`, `api.md`, `protocol.md` (the wire protocol), `development.md` (examples, benchmarks, tests). A change to behaviour goes in the page that covers it, and in the README only when it changes the pitch.

## Development Commands

```bash
npm test              # node --test "test/*.test.js": unit and integration tests, plus fixed-seed runs of the fuzzers
npm run test:bun      # the Bun-only tests in test/bun (bun:sqlite adapters, the Bun server and relay)
npm run test:types    # tsc over test/types against the declarations in types/
npm run test:coverage # the Node suite under c8; fails below 96% lines/statements, 88% branches, 92% functions
npm run fuzz          # a longer convergence campaign: node test/fuzz/run.js [--mode convergence|relay|hostile] [--seed N] [--runs N] [--steps N] [--clients N] [--run N --trace]
npm run fuzz:hostile  # the same with an attacker beside honest clients
node test/fuzz/run.js --mode relay   # half the clients behind a relay (src/relay) whose link drops and comes back
npm run bench         # server benchmark (bench/run.js); medians of 5 rounds
npm run bench:client  # client benchmark (bench/client.js) in happy-dom: React/Vue renders, list views, persistence
npm run bench:check   # both benchmarks with --check: every case under its ceiling, the client counts within their bounds
npm run bench:fanout  # (Bun) a store every client follows, published to by the server and written by its clients: direct, one relay, many relays (bench/fanout/)
bun bench/fanout/agent.js  # the server's machine in a two-machine bench:fanout; run.js --remote <host>:36700 on the other
bun bench/fanout/run.js --url wss://<host>/ws --clients 1000,5000  # clients alone against a deployment (through Caddy, relays): connects, writes, a reconnect storm
```

Run one test file with `node --test test/sync.test.js`, one test with `--test-name-pattern="..."`. A fuzz failure prints its seed and a reproduction command. CI (`.github/workflows/test.yml`) runs the tests on Node 22/24/26, the Bun tests, the coverage gate, the benchmark guard, and random-seed campaigns of the convergence (direct and relay) and hostile fuzzers; the publish workflow runs tests, types, the coverage gate and the Bun tests before `npm publish`.

- `src/relay/` — the follower store (`lazy-storage/relay`): `follower.js` (`createRelay`: per store a copy, the server's base read on the relay's own session and a queue of its clients' ops, answered from and decided as the server decides; `acknowledge: 'upstream'` vouches for each client and sends its ops up as its own, `'local'` acknowledges once queued, for a browser's tabs; no Node imports, the browser runs it), `copies.js` (`memoryCopies`), `storage.js` (`fileCopies`), `bun.js` (`createRelayHandlers`, `upstreamSocket`: `lazy-storage/relay/bun`)

- `src/index.js` — the client entry; it re-exports `LazyWatch` so apps drive `db.state` with the same copy lazy-storage uses (two copies do not recognize each other's proxies)
- `types/` — hand-written declarations, one file per export path; `test/types/` checks them
- `docs/` — the reference (see above); it ships in the npm package
- `examples/`, `bench/`, `test/` (`helpers.js` re-exports `createNetwork`/`fakeTime` and adds `seededRandom`; `test/fuzz/`: `convergence.js`, `hostile.js`, `run.js`; `test/bun/`)

## Architecture

- **Records and changes.** The top level of a store is declared in `initial`: `{}` is a collection of records keyed by id, a key in `singletons` (or a non-object value) one record. A record is a JSON object of any depth; arrays and paths declared in `registers` are leaves, written whole; `parents` names a child's parent field. A local batch on the client's proxy is compiled (`compile.js`) into one op `{ replica, seq, ts, changes }`, a change being `{ c, id?, path?, put | set | del }`. `null` means delete in a diff.
- **The rule.** Each record has a clock: `live` (per path, when a leaf was written or a container made: its birth) and `gone` (when a path inside a living record was deleted). Each change is decided on its own (`doc.js`): a write lands when its record and parent are there and nothing at its path is newer; a deletion when nothing at or beneath it is newer, a record's children included; nothing older than a container's birth lands beneath it; ties go to the later arrival. A deleted record leaves no clock. What lost is reported as `missing`, `newer` or `stale`. Timestamps are ms; clients stamp `max(wall + offset, highest + 1)`, the server clamps to its time and refuses ops older than the retention window as `expired`.
- **The client.** `db.state` is the base (`db.base`: the server's records with clocks, from snapshots asked with `clocks: true`) with the outbox replayed on top in replay mode; a patch or ack recomputes only the records it touched (`LazyWatch.overwrite`). The state has `inverse: true`, used both to revert a batch the shape refuses and by the undo manager (on unless `mirror: true`). A new op supersedes older pending writes to the paths it writes (`supersede`); the outbox and the base are persisted by the storage adapter. A reconnect sends a hello with the outbox and the version and epoch it knows; the server answers with a delta or a snapshot (inline, or over HTTP when large), and a refused op is taken back and reported as `rejected`.
- **The server.** A store is one doc (state and clocks), the replicas' progress, a delta log and a storage adapter; `rules`, `readOnly` and `validate` judge an op before it is decided. Commits are grouped: what one turn of the event loop merged is committed together at its end (`commitMany` where the adapter has it), and everything the store sends (acks, patches, answers, presence) is held until then and sent in order, through `later()` in `store.js`; `flush()`, session creation, evictions, HTTP snapshots, `export()` and `dispose()` commit first. Tests that read storage or a raw session's messages synchronously call `store.flush()` first. `store.on` listeners hear a batch as a diff on the next microtask. `store.state` is read-only by contract; server-side writes go through `store.patch(diff)` (authority mode), `store.del` or `store.apply(op, { user })`. SQLite adapters lease a store to one process, run versioned migrations on load, and can back up and restore while serving; a restore changes the store's epoch and clients hear `reset`.
- **Followers.** A relay (`src/relay/follower.js`) opens each store on one session of its own with `follower: true` and is sent clocks with its snapshots; for each client it asks `vouch` with the client's credential, and the server (`hub.js`, `follow.js`) judges it by the transport's own hooks and holds a grant on the follower's session, so an op, share or leave with `as` is the client's, and its ack and errors come back with `as` and `replica`. The relay's clients see its copy, base plus queue, decided by the same rule, so what they see while the server is away is what the server will decide, but for what only the server knows.

## Conventions

- Match the surrounding code: small modules, named functions, comments that say why and describe the design in prose (file headers explain the module's model). Keep the comment density of the file you edit.
- Tests use `node:test` and `node:assert/strict`, and drive clients and stores through `createNetwork` rather than sockets: "edit, `await net.settle()`, assert". A bug fix comes with a test that fails without it; a fuzz-found bug gets a pinned test.
- lazy-watch is a dependency, not a peer: its version lives in `package.json` and `bun.lock` (the tracked lockfile). `npm install` creates a `package-lock.json` the repo does not track; delete it. Bump with `bun install` after editing the range, and check the lockfile's integrity matches `npm view lazy-watch@<version> dist.integrity`.
- `CHANGELOG.md` follows Keep a Changelog. Work goes under `## [Unreleased]` (Added / Changed / Fixed / Security), each bullet a bold lead sentence and the what and why after it; a release turns the heading into `## [x.y.z] - YYYY-MM-DD` with a short summary paragraph under it that ends with what to check on upgrade.
- Commits: `feat:`, `fix:`, `chore:`, `release:` plus a subject in the imperative, and a body that explains the change. A release commit only moves the changelog heading and the version in `package.json`.
- Releasing is the maintainer's: they push master and create the GitHub release, whose `published` event runs the publish workflow (npm trusted publishing). Never push or tag. Push master before creating the release, or the tag lands on the previous commit.
